- 版本:v0.1(初稿)
- 日期:2026-07-26
- 状态:待评审

---

## a. 背景与目标

### 为什么做

开发者面对一个陌生的 GitHub 仓库,通常要花大量时间自己摸索:翻 README、猜目录结构、
逐条看 issues 和 commits,才能回答「这个项目是干什么的、怎么跑起来、代码从哪读起、
最近在改什么」。这些信息都在仓库里,但分散、无结构,读起来成本高。

大语言模型擅长归纳与问答,但直接把问题丢给通用聊天模型有两个缺陷:一是模型不知道
这个仓库的具体内容,容易凭空编造(幻觉);二是仓库内容量大且随时更新,不可能整体
塞进对话。解决办法是让模型以 **Agent** 的方式工作:需要什么信息就调用工具去仓库
现场取(目录树、README、issues、commits),再结合 **RAG** 从向量化后的仓库文档中
检索相关片段,让回答有据可依。

repo-scout 就是这样一个「GitHub 仓库导读 Agent」的完整实践:从基础对话到工具调用、
再到 RAG 与效果评估,按迭代逐步搭建。

### 给谁用

- **接手/选型新仓库的开发者**:快速了解一个项目能不能用、怎么用、代码结构如何。
- **开源项目的潜在贡献者**:想参与但不知从何入手,需要了解近期动向与上手路径。
- **学习 LLM 应用开发的工程师**:本项目同时是一个 Spring Boot 3 + LangChain4j
  构建 Agent/RAG 应用的参考实现。

### 项目目标

1. 提供一组 REST API:接入一个 GitHub 仓库后,可用自然语言就该仓库进行多轮问答。
2. 回答基于仓库真实内容(工具调用 + RAG 检索),而非模型的凭空发挥。
3. 支持一键生成仓库导读报告。
4. 具备可量化的效果评估手段与可复制的部署方式。

### 范围说明

- 一期只做 REST API,不做前端。
- 对话模型固定使用 DeepSeek API;向量化使用 LangChain4j 进程内 ONNX 模型
  `bge-small-zh`;业务数据存 MySQL,会话记忆存 Redis。技术栈已定,不在需求内讨论。

## b. 用户故事

1. **作为**一名要接手陌生项目的后端开发者,**我希望**输入仓库地址后直接问
   「这个项目怎么在本地跑起来」,**以便**不用自己在 README 和脚本里翻找运行步骤。
2. **作为**一名做技术选型的工程师,**我希望**询问「这个项目的整体架构和核心模块
   是什么」,并得到基于真实目录结构与文档的回答,**以便**快速判断该项目是否符合
   我们的需求。
3. **作为**一名开源项目的潜在贡献者,**我希望**问「这个仓库最近在修什么 bug、
   活跃度如何」,**以便**找到适合切入的 issue 与贡献方向。
4. **作为**一名多轮提问的用户,**我希望**追问时不用重复前文(如先问架构、再问
   「那刚才说的那个模块的入口在哪」),**以便**像和同事讨论一样连续对话。
5. **作为**本项目的开发者,**我希望**有一套批量评测脚本衡量回答质量,**以便**在
   调整提示词或检索策略后知道效果是变好还是变坏。

## c. 功能需求

按迭代分期。v0.1 为当前迭代,写到可直接开发的粒度;v0.2–v0.4 为概要,进入对应
迭代前再细化。

### v0.1 项目骨架、DeepSeek 接入、基础对话 + 会话记忆(详细)

#### FR-1.1 项目骨架

- **输入**:无(工程初始化)。
- **输出**:可启动的 Spring Boot 3 工程,分层清晰(controller/service/config 等),
  集成 MySQL、Redis 连接配置;提供健康检查端点 `GET /api/health`。
- **验收标准**:
  - `mvn spring-boot:run` 可在本地启动,无报错;
  - `GET /api/health` 返回 200 与服务状态 JSON;
  - 配置项(数据库、Redis、DeepSeek API Key)通过配置文件/环境变量注入,
    API Key 不出现在代码与仓库中。

#### FR-1.2 DeepSeek 模型接入

- **输入**:后端内部调用,传入提示词文本。
- **输出**:通过 LangChain4j 调用 DeepSeek API 返回的模型回复文本。
- **验收标准**:
  - 使用 LangChain4j 的抽象接入 DeepSeek(OpenAI 兼容协议),模型名、
    base-url、超时可配置;
  - API Key 缺失或无效时启动/调用给出明确错误信息,而非空指针等晦涩异常。

#### FR-1.3 基础对话 API

- **输入**:`POST /api/chat`,请求体含 `sessionId`(可空,空则新建会话)与
  `message`(用户消息,非空)。
- **输出**:JSON 响应,含 `sessionId` 与模型回复 `answer`。
- **验收标准**:
  - 首次请求不带 `sessionId` 时自动创建会话并在响应中返回;
  - `message` 为空或超长时返回 400 及可读错误信息;
  - DeepSeek 调用失败时返回统一错误结构,不向客户端泄露堆栈与密钥。

#### FR-1.4 会话记忆

- **输入**:同一 `sessionId` 下的多轮 `POST /api/chat` 请求。
- **输出**:模型回复能利用本会话的历史上下文(如正确解释「刚才说的那个」指代)。
- **验收标准**:
  - 会话历史存储于 Redis,服务重启后同一 `sessionId` 的上下文仍在;
  - 记忆有窗口上限(按消息条数或 token 数,可配置),超出后按策略截断,
    不导致提示词无限膨胀;
  - 会话设置过期时间(可配置),过期后自动清理;
  - 不同 `sessionId` 之间上下文互不串扰。

### v0.2 GitHub 工具集与 Agent 自主规划(概要)

#### FR-2.1 仓库接入

- **输入**:`POST /api/repos`,请求体含 GitHub 仓库地址(如 `owner/repo` 或完整 URL)。
- **输出**:仓库记录(存 MySQL),含基本元信息;无效地址或不存在的仓库返回明确错误。
- **验收标准**:合法公开仓库可成功接入并查询;重复接入幂等。

#### FR-2.2 GitHub 工具集

- **输入**:Agent 内部按需调用,参数为仓库标识及各工具自身参数。
- **输出**:四类工具的结构化结果:目录树、README 内容、issues 列表(可按状态过滤)、
  最近 commits。
- **验收标准**:各工具对典型公开仓库返回正确数据;GitHub API 限流与网络失败有
  重试/降级与可读报错。

#### FR-2.3 Agent 自主规划调用(Function Calling)

- **输入**:绑定了某仓库的会话中的自然语言问题(如「最近在修什么 bug」)。
- **输出**:Agent 自主决定调用哪些工具、取回结果后综合生成回答。
- **验收标准**:对「怎么运行/结构如何/最近动向」三类典型问题,Agent 能选择正确
  工具并给出基于真实数据的回答;工具调用轨迹可在日志中追溯。

### v0.3 文档向量化 + RAG 问答、仓库分析报告(概要)

#### FR-3.1 仓库文档向量化

- **输入**:已接入仓库的文档类内容(README、docs 目录等)。
- **输出**:切分后的文档块经 `bge-small-zh` 向量化并入库,可按相似度检索。
- **验收标准**:接入仓库后可触发/自动完成向量化;重复执行不产生重复数据。

#### FR-3.2 RAG 问答

- **输入**:仓库相关的自然语言问题。
- **输出**:检索相关文档片段注入上下文后的回答,附引用来源(文件路径)。
- **验收标准**:文档中有据可查的问题,回答与文档一致且带出处;检索不到时明确
  说明,而非编造。

#### FR-3.3 仓库分析报告

- **输入**:`POST /api/repos/{id}/report` 或等价触发方式。
- **输出**:结构化导读报告(项目定位、技术栈、目录结构解读、上手指引、近期动向)。
- **验收标准**:对典型公开仓库生成的报告各节非空、与仓库实际内容相符。

### v0.4 效果评估、Docker 部署、文档收尾(概要)

#### FR-4.1 效果评估脚本

- **输入**:预置的评测问题集(含预期要点)。
- **输出**:Python 脚本批量调用 API,输出评分与汇总报告。
- **验收标准**:一条命令可跑完整评测;结果可横向对比不同版本/参数的效果。

#### FR-4.2 Docker 部署

- **输入**:项目源码与配置。
- **输出**:Dockerfile 与 docker-compose(应用 + MySQL + Redis)一键启动。
- **验收标准**:干净环境 `docker compose up` 后核心 API 可用。

#### FR-4.3 文档收尾

- **输入**:各迭代产出。
- **输出**:完善的 README、API 文档、部署说明。
- **验收标准**:新用户仅凭文档可完成部署并跑通主流程。

## d. 非功能需求

### 响应时间预期

- 普通对话(不含工具调用):常规情况下 10 秒内返回,主要耗时在 DeepSeek API。
- 含工具调用/RAG 检索的问答:常规情况下 30 秒内返回。
- 仓库分析报告等重型任务:允许更长耗时,接口设计需考虑异步或明确的超时策略。
- 上述为体验目标而非硬性 SLA;所有外部调用(DeepSeek、GitHub)必须设置显式超时,
  不允许无限等待。

### API 调用成本控制

- 会话记忆设窗口上限,避免上下文无限增长导致 token 消耗失控。
- 工具返回内容(如目录树、issues 列表)注入提示词前做条数/长度裁剪。
- Agent 单次问答的工具调用轮数设上限,防止循环调用。
- 对用户消息长度设上限;记录每次调用的 token 用量,便于观测成本。
- Embedding 采用进程内 ONNX 模型,不产生外部 API 费用;向量化结果持久化复用,
  避免重复计算。

### 错误处理原则

- 对外统一错误响应结构(错误码 + 人类可读信息),不向客户端泄露堆栈、密钥等
  内部细节。
- 区分错误类别并映射合适的 HTTP 状态码:参数错误(4xx)、外部依赖失败
  (DeepSeek/GitHub 不可用、限流)、内部错误(5xx)。
- 外部依赖失败时给出可行动的提示(如「GitHub API 限流,请稍后重试」),关键路径
  可配合有限重试。
- 模型检索不到依据时应承认「不知道/仓库中未找到」,不编造答案。
- 服务端日志记录失败上下文(不含敏感信息),便于排查。

### 安全与鉴权范围

- 一期(v0.1–v0.4)REST API **不做认证鉴权**,接口仅用于本地/内网演示环境,
  不暴露到公网;对外开放前必须先补充鉴权方案(不在一期范围内)。
- 敏感配置(DeepSeek API Key、数据库口令、Redis 口令等)**仅通过环境变量注入**,
  不写入代码、配置文件明文或仓库;日志与错误响应中不得输出上述敏感信息。

## e. 名词表

| 名词 | 通俗解释 |
| --- | --- |
| **LLM(大语言模型)** | 能理解和生成自然语言的 AI 模型,本项目用 DeepSeek。可以把它当成一个「读过海量文本、会聊天的大脑」,但它默认不了解你给的具体仓库。 |
| **Agent(智能体)** | 不只「一问一答」,还能自己做计划、决定调用什么工具、拿到结果后继续思考的 LLM 应用形态。类比:普通聊天是「问路人」,Agent 是「雇了个助理,他会自己去查资料再回复你」。 |
| **Function Calling(函数调用/工具调用)** | 让模型能「点菜」的机制:开发者预先声明一批工具(如「获取目录树」「查 issues」),模型根据问题决定调用哪个、传什么参数,程序执行后把结果还给模型继续作答。 |
| **Embedding(向量化)** | 把一段文字变成一串数字(向量),语义相近的文字向量也相近。这样「怎么启动项目」就能匹配到写着「运行方式」的文档段落,即使字面不同。本项目用 `bge-small-zh` 模型在本机完成。 |
| **RAG(检索增强生成)** | 先「查资料」再「写答案」:提问时先从向量库里检索最相关的文档片段,连同问题一起交给模型,让回答有真实依据、减少编造。类比:开卷考试——先翻到相关页,再作答。 |
| **向量库(Vector Store)** | 存放向量化后文档片段、支持「按语义相似度查找」的存储。 |
| **会话记忆(Chat Memory)** | 让模型记住本轮对话历史的机制,多轮追问时不用重复背景。本项目存放在 Redis 中,并设窗口与过期策略。 |
| **幻觉(Hallucination)** | 模型一本正经地编造不存在的事实。RAG 与工具调用的主要目的之一就是抑制幻觉。 |
| **Token** | 模型处理文本的计量单位(约等于词或字的碎片),API 按 token 计费,也决定上下文长度限制。 |
| **提示词(Prompt)** | 发给模型的完整输入,包括系统指令、对话历史、检索到的资料和用户问题。 |
